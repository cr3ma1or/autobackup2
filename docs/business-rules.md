# Business Rules & Operational Logic Specification

## 1. Конечный автомат узла (State Machine)

Secondary-сервер функционирует в рамках трех состояний:

┌────────────────────────────────────────────────────────┐
│ STANDBY (Резерв) │
│ - DNAT перенаправляет трафик портов на Primary Node │
│ - Локальный x-ui в режиме горячего ожидания │
│ - Синхронизация БД разрешена по таймеру и CLI │
└───────────────────────────┬────────────────────────────┘
│
Авария Primary Node │ xui-failover promote (ручной ввод)
▼
┌────────────────────────────────────────────────────────┐
│ PROMOTED (Боевой узел) │
│ - Файл /etc/x-ui/standby-mode содержит 'PROMOTED' │
│ - Наличие блокировки /run/xui-standby.lock │
│ - DNAT отключен, трафик замыкается на локальный Xray │
│ - СИНХРОНИЗАЦИЯ СТОРОННИХ БЭКАПОВ БЕЗУСЛОВНО ЗАПРЕЩЕНА│
└───────────────────────────┬────────────────────────────┘
│
Восстановление Primary │ xui-failover standby (подтверждение)
▼
┌────────────────────────────────────────────────────────┐
│ RECONCILING (Сверка) │
│ - Экспорт изменений, накопленных за время аварии │
│ - Синхронизация временно заблокирована │
│ - Возврат в режим STANDBY │
└────────────────────────────────────────────────────────┘

### BR-101: Защита боевого режима (Split-Brain Prevention)

- Файл `/etc/x-ui/standby-mode` является обязательным маркером состояния. Только точное значение `STANDBY` разрешает репликацию; `PROMOTED`, `RECONCILING`, отсутствие или некорректное содержимое блокируют её.
- Если существует `/run/xui-standby.lock`, модуль `xui-standby-sync` также немедленно прерывает выполнение.
- Снятие блокировки ключом `--force` в режиме `PROMOTED` категорически запрещено.

### BR-102: POSIX-коды прерывания

Bash-скрипты устанавливают traps и завершаются с кодом `130` при `SIGINT` и `143` при `SIGTERM`. Эти коды сохраняют стандартную семантику systemd/оркестратора; секретные временные файлы очищаются обработчиком завершения.

## 2. Политики создания и ротации резервных копий (Primary Node)

### BR-201: Снятие согласованного снимка SQLite

- Резервная копия боевой БД `/etc/x-ui/x-ui.db` снимается без остановки сервиса исключительно командой:
   `sqlite3 "$DB_PATH" ".backup '$TEMP_DB_COPY'"`
- Прямое бинарное копирование через `cp` запрещено из-за активного режима WAL.

### BR-202: Защита оперативной памяти (OOM Prevention)

- Все промежуточные файлы бэкапа создаются строго на физическом накопителе в `${BACKUP_DIR}/.work`. Использование `/tmp` и `/run` (tmpfs) запрещено.
- Требование к свободному месту:
   `FreeSpace(BACKUP_DIR) >= 3 * Size(x-ui.db) + 50 MB`

### BR-203: Атомарная публикация и Sidecar Checksum

- Порядок публикации файла архива:
1. Создание зашифрованного архива: `*.tar.gz.gpg.part`.
2. Расчет хеша: `sha256sum "$part_file" > "$final_sha256_file"`.
3. Атомарное перемещение: `mv -f "$part_file" "$final_archive_file"`.

### BR-204: Двухуровневая ротация

- Лимиты: `MAX_AGE_DAYS=14`, `MAX_SIZE_GB=2`.
- Защитный барьер: `KEEP_MIN_ARCHIVES=3` является безусловным приоритетом над очисткой по размеру.

## 3. Политика карантина и нулевого доверия (Secondary Node)

### BR-301: SSH Forced Command

- Вызов приемника выполняется строго через `authorized_keys` под пользователем `xbackup` с белым списком IP источника `from="<PRIMARY_IP>"`.
- Входные аргументы валидируются регулярным выражением:
   `^xui-backup-put\s+([A-Za-z0-9._-]+)\s+([0-9]+)\s+([0-9a-fA-F]{64})$`

### BR-302: Изоляция поврежденных данных (Quarantine)

- Любой файл, не прошедший сверку размера или контрольной суммы, перемещается в `/opt/xui-backups/invalid/` с добавлением суффикса `.corrupt.<timestamp>`.
- Срок хранения файлов в карантине — `KEEP_INVALID_DAYS=7`.

## 4. Бизнес-правила транзакционного слияния (Standby Sync)

### BR-401: Разделение Planner и Engine

- Фаза 1 (Planner): Открывает исходную и целевую базы строго в `mode=ro`, формирует неизменяемый объект плана `SyncPlan`. Нулевая модификация ФС.
- Фаза 2 (Engine): Останавливает `x-ui`, создает персистентный снапшот, проводит транзакцию слияния, валидирует инварианты и запускает сервис.

### BR-402: Критерий свежести бэкапа

- Автоматическая репликация разрешена, если возраст архива не превышает 26 часов (`MAX_BACKUP_AGE_HOURS=26`).

### BR-403: Слияние клиентов (Dual-Layer Merge)

1. **Идентификатор:** Первичный поиск записи выполняется по ключу `uuid` (fallback — `email`).
2. **Первичный ключ:** Локальный `id` записи в таблице `clients` на Secondary Node сохраняется неизменным. Для новых пользователей генерируется новый автоинкрементный идентификатор.
3. **Привязка к Inbound:** Внешний ключ `clients.inbound_id` динамически заменяется на локальный ID целевого инбаунда.
4. **Синхронизация JSON:** Атомарно обновляется JSON-массив `"clients": [...]` внутри таблицы `inbounds` в поле `settings`.

### BR-404: Защита от массового удаления (Mass-Deletion Guard)

- Если количество клиентов к удалению превышает 50% от текущей базы Standby, транзакция блокируется с генерацией ошибки `CRITICAL`.

## 5. Защита инвариантов хоста (Host Identity Preservation)

### BR-501: Неприкосновенные параметры

Следующие параметры Secondary Node строго запрещено перезаписывать данными с Primary:

- `settings.webPort` (хостовый инвариант: `60291`).
- `settings.subPort` (хостовый инвариант: `2096`).
- `settings.subURI` (локальный endpoint подписок).
- `settings.tgBotEnable` (хостовый инвариант: `false`, во избежание Telegram 409 Conflict).
- `settings.*CertFile` / `*KeyFile` (локальные пути к SSL-сертификатам).
- `inbounds.port` для Inbound 1 (фиксирован на `443`).
- `inbounds.stream_settings` для Inbound 1 (локальные Reality-сертификаты и SNI).
- `inbounds.externalProxy` (публичный IP Secondary Node).

### BR-502: Разрешенные к репликации параметры

Из таблицы `settings` переносятся исключительно:

- `subEnableRouting` (принудительно устанавливается в `'true'`).
- `subRoutingRules` (актуальная base64-строка правил клиентского сплит-туннелирования).

### BR-503: Проверка целостности и инвариантов (Post-Merge Assertions)

- Перед вызовом `COMMIT` сверяются значения инвариантов с состоянием до начала транзакции. При любом отклонении инициируется `ROLLBACK`, восстановление из снапшота и аварийный перезапуск службы.
